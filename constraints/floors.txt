# The declared floors, pinned exactly. Installable, and installed by the
# `dependency-floor` CI job.
#
# Why this file has to exist: pip has no "resolve to the lowest permitted
# version" mode. A floor of `transformers>=4.56` is satisfied by whatever is
# newest, so a job that only reads pyproject tests the ceiling and calls it the
# floor. Every direct dependency therefore gets an `==` here, and this file is
# what makes the floor claim measurable.
#
# torch is deliberately absent: its CPU wheels live outside PyPI, so the job
# installs it by hand from the torch index before applying these. Its floor is
# version-dependent (see pyproject) and cannot be expressed as one pin.
#
# When a floor in pyproject changes, change it here in the same commit. A
# mismatch means the job is testing a version nothing declares.

transformers==5.10.1

# deliberately ABOVE the floor it tests, and the reason is a collision between two declared
# floors rather than a preference.

# a cp310 wheel, which is what this job's Python 3.10 needs. The pin stays exact for the original
# reason: an unpinned pyarrow resolves to whatever is newest and builds from source the day that

# numpy is not a declared dependency of this project and is pinned here anyway.
#
# THE ORIGINAL REASON NO LONGER APPLIES, and saying so is cheaper than letting the next reader
# trust it: pyarrow 14's extension modules are compiled against numpy 1 while its metadata said
# only `numpy>=1.16.6`, so the resolver paired it with numpy 2 and the job failed with
# "ImportError: numpy.core.multiarray failed to import" from `pyarrow.lib`. pyarrow is pinned at
# 23.0.1 here now, built for numpy 2, so that collision is gone.
#
# WHAT IS NOT PROVEN, said rather than left for the job to discover: pyarrow 23.0.1 declares no
# numpy bound at all, so nothing in the metadata forces numpy 2 and nothing proves its compiled
# extension imports against numpy 1.26.4. The resolve is satisfiable; the import is what the
# floors job actually tests. If it fails at `import pyarrow.lib`, this pairing is the cause.
#
# THE PIN STAYS ANYWAY, as a deliberate hold rather than a forced one. This environment has
# never been exercised on numpy 2, and `accelerate==0.26` predates numpy 2 entirely. Moving the
# datasets floor and the numpy major in one commit would make a failure unattributable, which is
# the opposite of what a floors job is for. 1.26.4 is the last numpy 1 and supports Python 3.10.
# Lifting it is a separate, deliberate step with its own measurement.
numpy==1.26.4
